# DECISIONS
- Stage 0: git top-level is this folder already; no parent repo problem. No `git init` needed.
- GitHub trees API verified here: `HEAD` accepted (200), shape {sha,url,tree,truncated}, CORS *, 404 for missing repo, limit 60/h. HEAD-then-default_branch fallback is still implemented.
- `modified` costs a lot: abbreviated packuments measured at 29 KB (ms), 780 KB (fastify), 1.2 MB (eslint), 8.7 MB (typescript), versus 2-7 KB for `/<name>/latest`. So the crawl builds the tree from `/latest` only, and `modified` is fetched in a separate optional second pass (`withModified`), so the tree/animation never waits for it. Missing `modified` contributes 0 staleness to fragility.
- Node 24 rejects `node --test test/`; the test command is `node --test test/*.test.mjs` (`npm test`).
- Crawl is level-synchronous BFS (8 parallel within a level): simpler than a worker pool, deterministic levels.
- Packages whose name is also a Node built-in (e.g. `events`, `buffer`) are never reported as ghosts: `require('events')` resolves to core, so we cannot tell.
- Removal tests (express, postcss) were run in throwaway clones outside the project, using the repos' own scripts. postcss needs pnpm (`npm install` fails with ERESOLVE), run through `npx pnpm@12.11.2` with the repo's lockfile. Tally: 4 candidates tested, 3 wrong, 1 unconfirmed, 0 confirmed unused (see results/removal-test*.md).
- Config-key rule: a top-level package.json key whose name equals a declared package counts as a mention. Added after the postcss test showed `simple-git-hooks` was a scanner bug. Metadata keys and dependency maps are in a skip-list and never count. The postcss removal test predates this fix.
- "Lower confidence" badge: general rule (scope equal to a used package's name, or name starting with `<used package>-`, parent at least 4 characters), no name lists. Heuristic, not validated, written after seeing postcss and debug.
- `validate.mjs --reuse` keeps depcheck's earlier output and re-runs only the scanner side, because depcheck does not depend on this code and three clones were later npm-installed (a fresh no-install run would be contaminated). `depcheck-installed.mjs --recompute` does the same for the installed comparison.
- The depcheck "installed" comparison used `npm install --ignore-scripts --legacy-peer-deps` in the clones (3 repos only).
- Every demo number in docs comes from a dated run; the UI contains none.
- Animation rework: the old viz repainted the whole web every frame; the profile showed the cost was native rasterization, not JavaScript (results/animation-perf.md). New design: a pure choreography module (src/choreo.js), a static canvas plus a small live canvas with dirty-rect clearing, time-based movement with a clamped delta, fixed effect pools, DPR clamped to 2, counters written at most 10 times a second.
- Layout for the animation is incremental: each package takes an equal share of its parent's wedge when the crawl delivers it and never moves, so the spider can build while npm is still answering. This replaced the layout by subtree size (it needs the finished tree). Known cost: crowded wedges on heavy branches. `src/layout.js` and its test were deleted because nothing else used them.
- Spider rules: nothing exists before the spider reaches it, the thread tip is the spider, returns walk existing threads only, spokes (declared dependencies) first, with nothing ready it waits and never wanders. Pace: first 15 packages at natural speed, then up to 14x, so 464 packages take about 23 s and 682 about 30 s.
- Cross threads (shared dependencies) are drawn once, faintly, after the build; they are the one thing the spider does not lay.
- Skip animation jumps to the finished state (including the prune); Replay re-runs from the cached result; both use the same path as `?fixture=` playback.
- Animation performance is measured on recorded scans (scripts/fixtures/*.json) in headless Chromium, with DPR 2 and 4x CPU throttle as the stress case. Numbers are from one machine, not a real GPU, Safari, Firefox or a phone.
- Dot colour legend (one line under the web, text depends on the staleness box at scan time). Measured on postcss (228 packages): with staleness OFF only two colours occur, green (2+ maintainers, 102 packages) and yellow (exactly 1 maintainer, 126 packages); age is not measured, so yellow does not mean old. With staleness ON the colours spread from green to red. The legend swatches are computed with the same `fragility()` as the dots, and a test checks that.
- Beautify branch: one palette object (src/theme.js) drives CSS variables and the canvas; four themes; default follows prefers-color-scheme, saved in localStorage (try/catch). 2.5D depth in canvas 2D + CSS only (no WebGL, no backdrop-filter, no external fonts). Dark themes use additive glow (`lighter`), Dawn Dew uses normal blending.
- Contrast was measured per theme (scripts/contrast.mjs, test/theme.test.mjs). Hex changes forced by the 3:1 rule against bg0/bg1/centre glow: dawn.c2 #0f9d8a -> #0e9280, dawn.cmiss #94a3b8 -> #768293, ember.cmiss #7c6a5c -> #8e7f73. Status text on the panel uses derived, contrast-adjusted variants (okText/warnText/badText), so the node colours stay as specified.
- Deuteranopia simulation (Machado 2009) showed yellow~orange nearly identical in Midnight (dE 15) and Dawn (dE 9) and teal~grey in Dawn (dE 8), so two non-colour cues are drawn in every theme: a ring for fragility >= 0.55 and hollow nodes for not-on-npm. The legend carries the same cues in its swatches and says so.
- The orange/red ring cue means "orange/red range", which is deprecated, or old (staleness on); the legend text says 'deprecated (ring)' / 'old, 1 maintainer, deprecated (ring)'.
- Idle state: the spider hangs from the top on a thread and sways; rings carry a slowly travelling highlight (live layer, idle only); a one-line hint sits below. The first scan continues the drop from where the spider hangs.
